本文件记录会影响未来工作的选择。条目按时间倒序排列；旧决策被替代时保留原文，并在状态和“后续”中链接新决策。

## D-010：由 Codex 自动整理笔记并设置本地临时区

- 日期：2026-09-17
- 状态：已采纳
- 背景：用户希望专注于学习和动手，不额外承担整理笔记的流程；同时需要一个不污染正式目录和 Git 历史的本地杂项空间。
- 决定：每次发生实质学习后，由 Codex 自动更新当日日记，并在知识形成稳定理解时更新主题笔记。笔记只依据用户在对话、代码、实验和修正中的可观察表现，区分独立完成、提示后完成和待验证。新增 `.tmp/` 作为本地杂项与短期中间文件目录，并整体排除 Git 版本控制。
- 理由：自动整理能够保持学习轨迹连续；证据约束可以避免把导师说明误记为用户掌握；独立临时区可以容纳无须复现的杂项而不混入正式成果。
- 影响：用户无需主动要求记笔记；实质学习会话结束前必须检查 `notes/`。任何需要复现、评审或跨会话保留的代码、结果和结论必须迁移到 `notes/`、`experiments/`、`projects/` 或 `docs/`，不能只存在于 `.tmp/`。
- 后续：从 L0 / M0 的第一次实质学习开始执行自动记录；定期从日记提炼主题笔记并清理失效的重复内容。

## D-009：学习产物按笔记、实验和贯穿项目分层

- 日期：2026-09-17
- 状态：已采纳
- 背景：学习路线与项目路线已经确定，需要一个既能支持按日成果积累，又不会让临时实验、知识记录和稳定项目代码相互污染的仓库结构。此前 [D-004](#d-004学习文档统一收敛到-docs) 将学习内容统一放入 `docs/`，适用于当时没有实验与项目的探索阶段，已不符合当前成果驱动模式。
- 决定：新增 `notes/`、`experiments/` 和 `projects/` 三个顶层目录。`notes/daily/` 记录过程，`notes/topics/` 沉淀稳定理解；`experiments/` 按 L/M 阶段和具体问题组织一次性验证；`projects/transformer-cuda-kernels/` 保存稳定实现、测试、Benchmark、PyTorch 接口、项目文档和小型结果。`docs/` 只保存项目记忆、稳定规划和管理文档。
- 理由：过程、证据和稳定成果具有不同生命周期；分层可以保留学习轨迹，同时确保最终项目不依赖临时代码，并让新会话快速判断内容应写入哪里。
- 影响：项目不得依赖 `experiments/` 才能构建；日记和主题笔记通过链接关联而不复制正文；小型结果摘要可以入库，构建产物、缓存和大型 Profiler 原始文件忽略。[D-004](#d-004学习文档统一收敛到-docs) 关于主题学习内容统一写入 `docs/` 的部分被本条替代。
- 后续：启动 L0 / M0 时在现有骨架中加入真实构建、测试和首个实验；只有出现明确职责缺口时才新增顶层目录。

## D-008：学习路线按知识依赖和掌握标准推进

- 日期：2026-09-17
- 状态：已采纳
- 背景：项目成果路线已经确定，但仍需单独明确学习内容、先后依赖、深度边界和掌握标准，避免把项目任务清单误当成知识规划，也避免前置课程无限扩张。
- 决定：采用 L0—L7 学习路线：开发闭环与最小系统基础、CUDA 执行模型、CUDA 内存模型与数据布局、并行协作与归约、数值计算与 Transformer 基础算子、CUDA 性能工程、PyTorch 自定义算子工程、综合复盘与求职准备。各阶段以掌握标准而非时间前进，并通过阶段出口映射到项目 M0—M6。C++、系统、数值和 PyTorch 基础只在主线触发实际阻塞时做最小补充。
- 理由：知识路线与项目路线分离后，可以分别回答“学到什么程度”和“交付什么成果”，同时通过阶段出口保持成果驱动；按需补基础能防止临近实习时陷入完整前置课程。
- 影响：后续教学必须遵守[学习规划](cuda-learning-plan.md)中的 P0/P1/P2 边界、掌握标准和回退规则；不得用阅读完成或示例跑通代替掌握，也不得新增固定时间表。
- 后续：设计最小仓库结构，盘点本机环境并从 L0 / M0 开始；实际推进中只在证据表明范围不合适时调整路线并记录原因。

## D-007：用 Transformer CUDA 算子库衔接学习阶段与项目成果

- 日期：2026-09-17
- 状态：已采纳
- 背景：成果驱动路线需要一个能从 CUDA 入门持续演进到性能优化和框架接入的贯穿项目；零散练习缺少简历叙事，单一复杂算子不适合当前基础，完整框架又会引入过多非核心工作。
- 决定：采用暂名 `Transformer CUDA Kernels Lab` 的迷你算子库作为贯穿项目。按 M0 项目骨架、M1 数据映射、M2 并行归约、M3 Transformer 基础算子、M4 系统化性能工程、M5 PyTorch 接入、M6 求职成果收口推进。每个里程碑同时规定必要知识、动手实验、项目版本和完成标准，详细内容见[成果路线](cuda-operator-roadmap.md)。
- 理由：基础 Elementwise、布局和 Reduction 能自然成为 Softmax、Norm 与融合算子的前置成果；同一项目可以从首个 Kernel 开始积累，并最终展示正确性、性能分析、优化证据和框架接入能力。
- 影响：后续不把学习章节和项目任务分成两条线；每次只补当前里程碑所需知识，并把有效实验合入项目。手写高性能 GEMM、完整 FlashAttention、推理引擎和多后端支持不属于首轮核心范围。
- 后续：确认里程碑粒度后设计最小仓库结构，盘点本机环境并启动 M0；M4 的代表性深度优化算子由 M1—M3 的实测结果决定。

## D-003：将收藏资料作为按问题取用的分层资料库

- 日期：2026-09-16
- 状态：已采纳
- 背景：`.resources` 同时包含两个内容重叠的通用 AI Infra 知识库、一个体量较大的 CANN 专项实践库和若干外部网站。如果按仓库或目录顺序全部学习，容易重复、跨越前置知识并过早固定方向。
- 决定：采用“地图—概念—验证”的分层用法：用 `ai_infra` 定位方向和主题，用 `AIInfraGuide` 补具体概念，仅在明确探索昇腾时使用 `cann-learning-hub` 实践；外部网站用于补充讲解、练习或进入官方生态。每个问题通常只选择一到三份材料。
- 理由：这种方式既能充分利用收藏，又符合当前问题驱动、逐步讲解和保持方向开放的教学边界。

- 后续：实际学习某个主题时继续校验对应资料的准确性和深度，并在必要时补充官方文档或原始论文映射。

## 新决策模板

复制以下模板到文件顶部，并将 `NNN` 替换为递增编号：

```markdown
## D-NNN：简短标题

- 日期：YYYY-MM-DD
- 状态：提议 / 已采纳 / 已替代 / 已拒绝
- 背景：要解决的问题和约束。
- 决定：选择了什么。
- 理由：为什么这样选，以及主要替代方案。
- 影响：对后续实现、学习或维护的约束。
- 后续：验证点，或替代本决策的新条目链接。
```
