# Transformer CUDA 算子库成果路线

- 状态：草稿，主线与阶段已确认，具体算子可根据实测调整
- 最后更新：2026-09-17
- 结论摘要：以一个持续演进的 Transformer CUDA 算子库贯穿学习。路线按成果依赖而非日期推进；每个阶段同时学习必要知识、完成动手实验并交付一个可验证的项目版本。

## 项目目标

项目暂名 `Transformer CUDA Kernels Lab`。最终成果不是零散 Kernel 合集，而是一套具备以下内容的迷你算子库：

- 若干从基础并行原语演进而来的 Transformer 相关 CUDA 算子；
- CPU 或 PyTorch 参考实现、自动正确性测试和边界测试；
- 统一的 Benchmark 与 Profiling 方法；
- 一个代表性算子的多版本优化过程和证据；
- PyTorch 自定义算子接入与实际调用示例；
- 可复现的构建说明、性能报告、设计取舍和简历摘要。

CUDA 算子开发是当前入门锚点。项目优先训练可迁移的 GPU 编程和性能分析能力，不承诺全面覆盖 Transformer，也不以超过成熟厂商库为成功标准。

## M0：可复现的 CUDA 项目骨架

### 对应学习阶段

建立最小开发闭环，只学习让 CUDA 程序可构建、可运行、可检查所需的内容：编译与链接、Host/Device、Kernel 启动、内存分配与拷贝、错误检查、同步和基础计时。

### 配套实验

- 记录操作系统、驱动、CUDA Toolkit、编译器、GPU 与可用显存等环境基线。
- 运行一个最小 Kernel，观察去掉同步或错误检查后现象如何变化。
- 比较 CPU 计时、CUDA Event 计时以及包含/不包含数据传输时的结果。

### 项目成果

- 能够构建并运行的最小项目；
- 第一份正确性测试；
- 第一份 Benchmark 输出；
- 环境与复现说明。

### 完成标准

- 能解释从 Host 发起调用到 Kernel 完成的基本过程；
- 构建、运行、测试和计时路径彼此分离；
- CUDA 错误不会被静默忽略；
- 重复测量结果具有基本稳定性，且明确计时范围。

## M1：GPU 编程模型与数据映射

### 对应学习阶段

理解 Grid、Block、Thread、Warp 与数据之间的映射，并按需补充一维/二维数组、指针、连续内存、行列布局和边界处理。

### 配套实验

- 改变 Block 大小和输入规模，观察线程覆盖、越界与性能变化。
- 对比连续访问与跨步访问。
- 对比一维扁平索引和二维索引的正确性与访问方式。
- 通过简单 Elementwise/Transpose 类任务观察数据布局的影响。

### 项目成果

- 一组基础 Elementwise Kernel；
- 二维数据映射或布局变换 Kernel；
- 连续访问与跨步访问的对比数据；
- 线程—数据映射说明图或文字说明。

### 完成标准

- 能在编码前写出线程到数据的映射关系；
- 任意合法输入规模都不会因边界处理产生错误；
- 能解释一次访存模式变化为何影响性能；
- 测试覆盖非整除 Block 大小的形状。

## M2：并行归约原语

### 对应学习阶段

从 Reduction 学习并行协作：Shared Memory、同步、竞争、Warp 执行、Shuffle、资源使用和多阶段归约。它是后续 Softmax、Norm 等算子的直接前置。

### 配套实验

- 从朴素或低并行度基线开始，逐步增加并行度。
- 对比全局内存中间结果、Shared Memory 和 Warp 级通信。
- 故意移除一次必要同步，观察错误是否稳定出现，并解释其不确定性。
- 对不同长度、非二次幂长度和不同数值范围进行验证。

### 项目成果

- 至少三个可比较的 Reduction 版本；
- 覆盖常见边界的正确性测试；
- 一份版本演进表，记录每版假设、资源使用和性能；
- 首次基于证据淘汰不合理优化。

### 完成标准

- 能解释每个线程、Warp 和 Block 各自负责的数据；
- 能指出同步位置及其必要性；
- 正确性不是只在单一形状上成立；
- 性能比较使用相同输入、预热、重复次数和计时口径。

## M3：Transformer 基础算子

### 对应学习阶段

把并行原语组合成真实算子，学习数值稳定性、张量形状、数据类型、融合机会以及“数学等价不等于实现等价”。

### 配套实验

- 比较朴素指数计算和减去最大值后的 Softmax。
- 改变行宽、Batch、数据分布与数据类型，观察误差和性能。
- 用 Reduction 原语构造 Softmax 和 RMSNorm/LayerNorm。
- 将相邻逐元素步骤合并，分开测量内存流量与 Kernel 启动影响。

### 项目成果

- 数值稳定的 Softmax；
- RMSNorm 或 LayerNorm；
- 至少一个融合的逐元素或归一化相关算子；
- 多形状、多数值范围的测试矩阵。

### 完成标准

- 能说明算子的数学定义、并行拆分和数值稳定处理；
- 与参考实现的误差满足明确记录的容差；
- 对连续性、形状和数据类型的支持范围有清楚说明；
- 每个融合版本都有问题假设和测量证据，而非仅减少代码行数。

## M4：系统化性能工程

### 对应学习阶段

将早期一直使用的基础计时升级为系统化分析：吞吐量与延迟、预热与同步、内存带宽、算术强度、Occupancy、寄存器与 Shared Memory 使用，以及 Nsight Systems/Compute 的分工。

### 配套实验

- 用一个故意存在访问问题或资源问题的 Kernel 验证工具指标。
- 比较端到端时间与纯 Kernel 时间，解释两者差异。
- 对代表性算子建立朴素版、优化版和参考实现的统一测试矩阵。
- 改变形状，寻找优化收益消失或反转的边界。

### 项目成果

- 统一 Benchmark 协议；
- 可复现的 Profiling 命令或操作说明；
- 一个代表性算子的多轮优化历史；
- 包含环境、形状、数据类型、指标和限制的性能报告。

### 代表性算子选择门

到达本阶段后，依据 M1—M3 的实测结果，从 Softmax、RMSNorm/LayerNorm 或融合算子中选择一个作为深度案例。选择标准是：已有正确基线、存在可解释瓶颈、设备能够稳定测量、范围适合独立完成。当前不提前承诺手写 GEMM 或 FlashAttention。

### 完成标准

- 每项优化都形成“假设—指标—修改—结果—解释”闭环；
- 报告区分 Kernel 时间、数据传输和框架开销；
- 不用单一形状或一次测量声称普遍加速；
- 能解释优化在哪些输入条件下无效或退化。

## M5：PyTorch 自定义算子接入

### 对应学习阶段

学习 Python、C++、CUDA 与 PyTorch 的边界，以及算子注册、构建、参数检查、设备、数据类型、连续性和测试。只有独立 Kernel 已经正确且可测量后才进入本阶段，避免同时调试算法、CUDA 和框架接入。

### 配套实验

- 先接入一个最简单的已验证 Kernel，再迁移复杂算子。
- 分别触发错误设备、错误数据类型、非连续输入和非法形状。
- 比较独立程序与框架调用的计时差异。
- 若算子需要训练场景，再单独评估是否增加反向；默认不强行覆盖 Autograd。

### 项目成果

- 可由 PyTorch 调用的 CUDA 自定义算子；
- 参数校验和清晰错误信息；
- 与参考实现对比的集成测试；
- 最小调用示例和安装/构建说明。

### 完成标准

- 新环境能按文档完成构建和基本调用；
- 支持范围和不支持情况明确；
- 框架集成测试与独立 Kernel 测试均通过；
- Benchmark 明确包含或排除了哪些框架开销。

## M6：项目收口与求职表达

### 对应学习阶段

把学习过程整理为工程成果，补齐复现、证据、取舍和表达，而不是临近投递时根据记忆包装项目。

### 配套实验

- 从干净构建开始复现关键结果。
- 对最终表格中的数据重新运行，并检查环境和口径。
- 用一个小型 Transformer 片段或等价调用链展示算子如何被使用；不扩张为完整推理引擎。
- 针对结果准备失败案例、退化场景和后续改进方向。

### 项目成果

- 清晰的 README、项目结构说明和端到端演示；
- 最终正确性与性能报告；
- 关键优化的演进记录；
- 一条准确的简历描述；
- 能从基础原理追问到实现细节的面试问题清单。

### 完成标准

- 第三方仅依据文档即可理解项目目标、构建方法、测试方法和结论边界；
- 简历中的每个数字都能对应到可复现条件和原始结果；
- 能解释至少一次失败优化及从中得到的结论；
- 项目展示的是问题解决能力，而不是文件数量或技术名词数量。

## 每次学习的标准成果闭环

每次正常推进只选一个能够闭环的小问题：

1. **当前问题**：它阻止哪个里程碑完成？
2. **必要知识**：只学习解决问题所需的一层概念。
3. **事前预测**：写下预期现象及理由。
4. **最小实验**：只改变一个主要变量，并保留参考基线。
5. **结果验证**：检查正确性、测量口径和可重复性。
6. **项目合入**：把有效结果纳入测试、Kernel、工具或文档。
7. **证据记录**：保存环境、输入、指标、结论与限制。
8. **下一节点**：根据未满足的完成标准选择下一项，而不是按日期推进。

一次学习不必完成整个里程碑，但结束时应产生至少一种可检查的增量：代码、测试、实验数据、图表、结论、问题定位或设计决策。

## 主线外内容

以下内容不进入首轮核心里程碑，只有在主线成果提出真实需求时才加入：

- 完整深度学习框架或推理引擎；
- 分布式训练与多机通信；
- 手写高性能 GEMM、Tensor Core 极限调优；
- FlashAttention 完整复现；
- CUTLASS、复杂模板元编程；
- Triton 重写全部算子；
- Blackwell 特有特性的专项优化；
- 同时支持 CUDA、CANN 和其他硬件后端。

可选扩展应在 M6 核心成果完成后，或能够直接解决代表性算子的明确瓶颈时再评估。

## 资料使用

- 用 `AIInfraGuide` 的 CUDA 编程模型、内存模型、性能优化、Reduce、Softmax 和性能工具章节补当前节点所需概念。
- 用 `ai_infra` 的 CUDA/HPC 板块定位主题、检查简历成果表达和面试追问，但不直接套用其现成项目数字或代码。
- 框架接入阶段优先查当时版本的 PyTorch 官方自定义算子文档；环境、GPU 架构、工具参数和 API 等时效性信息以官方一手资料与本机实测为准。

## 开放问题

- 本机操作系统、驱动、CUDA Toolkit 和 PyTorch 环境尚未盘点。
- 项目使用 `projects/transformer-cuda-kernels/`，代码、测试、Benchmark、框架接口、文档和结果目录职责已经确定；具体构建文件随 M0 加入。
- M4 的代表性深度优化算子应根据 M1—M3 实测结果选择。
- 是否实现反向传播、半精度或 Triton 对照版，需由核心成果的实际需要决定。
